# Supermetry query-engine performance audit

Audited commit `93c5d59` read-only; `internal/query/sql_hot.go` was excluded because another job owns it. Measurements used `EXPLAIN (ANALYZE, BUFFERS)` on `supermetry_dev`, site 1, a 30-day range, and an Asia/Kolkata session. The database held 25,361 events, 3,813 hot sessions, and 3,037 closed sessions. Times are warm-cache development measurements, not projections.

| Rank | Location | What is slow; measured evidence | Why | Concrete fix |
|---:|---|---|---|---|
| 1 Critical | `internal/query/vitals.go:150-188,296-314` | A Web Vitals property filter took **421.2 ms**, returning 1,973 matches after **6,914,458** join-filter rejections; an event filter took 241.7 ms/3,925,066 rejections. With a dimension, `Vitals` runs the range again at lines 51-70. | The correlated event `EXISTS` has no day/`ts` bounds; poor cardinality estimates select a nested-loop semi join over thousands of materialized events. This is already near the 300 ms target at 25k rows. | Build one bounded relation and join it: `WITH matched AS MATERIALIZED (SELECT DISTINCT site_id,retention_class,local_day,session_id FROM events WHERE site_id=$1 AND retention_class=$2 AND local_day BETWEEN $3 AND $4 AND ts >= $5 AND ts < $6 AND kind=1 AND <filter>) ... JOIN matched USING (...)`; return overall + breakdown with `GROUPING SETS` in one scan. |
| 2 High | `internal/query/events_explore.go:299-337` | Listing 51 recent events took **19.5 ms** after scanning, joining and top-N sorting **25,341 rows** (600 buffer hits). | The only general event index is BRIN on `ts`; keyset pagination does not help the first page because PostgreSQL must scan/sort the whole range. Cost grows with all events in the requested range. | After write-cost benchmarking, add a leaf-propagated btree matching the keyset order: `(site_id, ts DESC, session_id DESC, kind DESC, name_id DESC, path_id DESC)`; keep `local_day`/`ts` predicates for pruning. |
| 3 High | `internal/query/funnel.go:134-150` | The hot sequence scan took **15.3 ms execution + 9.6 ms planning**, read 13,940 page/custom events, and opened **41 event leaves** for 3,420 sessions. | The event join has only `(site_id,session_id,kind)`; it omits retention class, `local_day`, and `ts`, defeating both LIST and RANGE pruning. | 4 High | `internal/query/goals.go:79-112` | A hot `/` page-goal predicate took **10.4 ms execution + 8.6 ms planning**, scanning **41 leaves/7,509 pageviews** before 2,550 session index probes. `sql_hot.go` consumes these predicates but was not reviewed. | Page/scroll/event goal subqueries omit retention/day/time constraints; page and scroll aliases are not repaired elsewhere. | Emit `ge.retention_class=s.retention_class AND ge.local_day=s.local_day AND ge.ts >= $start AND ge.ts < $end` (same for `ce`), passing explicit range args rather than string rewriting. |
| 5 High when imports exist | `internal/query/sql_imported.go:106-119` | `firstNativeDay` took **9.6 ms execution + 31.8 ms planning**, scanning **41 session + 41 event leaves**, 3,813 sessions and 25,361 events. | `min(local_day)` has neither retention nor range-key constraints and is recomputed on eligible requests whenever imports exist. | Persist `first_native_day` per site when the first native row/day closes, or derive/cache it from indexed `day_close`/rollup metadata; remove raw `sessions` and `events` minima. |
| 6 Medium | `internal/api/handlers_stats.go:80-92,113-170`; `internal/query/plan.go:189-239,277-295` | **Inference (Go orchestration):** a 30-day exact weekly request performs an initial query whose rows are discarded, then 5 sequential `Engine.Query` calls; comparison doubles the bucket calls. At minimum remove the discarded initial query and enforce a request-wide deadline/bucket cap. |
| 7 Medium at hosted scale | `internal/platform/store/keys.go:40-45`; `internal/platform/keys/keys.go:169-181` | Every public request uses a sequential `api_keys` scan: **0.020 ms/1 row** today. The table has no `prefix` index, while `hash` is unique-indexed. | Authentication cost becomes O(all keys), on every request. | Compute SHA-256 before lookup and query `WHERE hash=$1` using the existing unique index; then constant-time compare the returned hash defensively. |
| 8 Medium | `internal/query/cache.go:23-59`; `internal/query/plan.go:160-296`; `internal/query/sql_rollup.go:293-314` | **Inference:** the implemented 1,024-entry closed-result LRU has no production caller; every request also reloads close/block metadata. | Immutable closed-range dashboards are recomputed despite a version-aware cache already existing. | Wrap closed-only normalized queries with `CacheKey(site,query,closedThrough,maxVersion)` and singleflight; cache `closedThrough`/block maps by site+close version. Never long-cache hot/current ranges. |
| 9 Medium background | `internal/closer/closed.go:11-65,126-143`; `internal/closer/cubes.go:3-15`; `internal/closer/rollup.go:12-98` | **Inference:** day close revisits the same event day for pageviews, engagement, custom sequence, attribution, profile, and custom-close, then repeatedly scans/unnests closed sessions for each derived table. | Repeated full-day passes compete with request traffic as volume rises; raw predicates cannot prune the retention-class LIST level. | Materialize a bounded `candidate_events` result once per site-class/day close and derive sequences/custom rows from it; compute/store session scroll sums once, then feed all rollups from the same per-session relation. |
| 10 Medium upgrade path | `internal/closer/backfill.go:65-84,214-250`; `cmd/supermetry/serve.go:450-458` | **Inference:** backfill performs one cursor query + transaction + rollup set per site-day and sleeps 1 second after each; 100 sites × 365 days implies **10.1 hours of sleeps** alone. | Site-day N+1 work and `(day,site_id)` ordering do not match the `day_close(site_id,day)` PK. | Fetch/process bounded batches ordered by day; recompute one day for many sites, checkpoint per batch, and consider partial `(day,site_id) WHERE status='done'` only after plan measurement. |
| 11 Low/medium polling | `internal/realtime/realtime.go:54-101` | **Inference:** each rich realtime poll scans the in-memory store twice (`ActiveSince`, then `RealtimeSnapshot`) and rereads the same 29 closed minute rows. | Dashboard polling multiplies CPU/allocations and small DB reads as active sessions grow. | Produce 5m + 30m values in one store pass; cache per-site rich snapshots for 1-5 seconds and closed-minute rows until the next minute boundary. |

## Checked and fine

- Session page filters and closed property filters were decorrelated into hash/semi joins: **11.7 ms** for 3,808 sessions/25k events and **2.2 ms** for 3,037/5,502 rows; no per-row large-table scan occurred.
- Profile lookup in session listing used the partial `(site_id,profile_id,ts)` index: **7.7 ms**, 381 lateral loops, zero profile rows; profiles are disabled on site 1.
- Closed/custom/cube/visitor/rollup/import aggregate queries constrain `day`; event explore, journey, and raw retention outer scans constrain both civil day and half-open `ts`.
- `$n::date` parameters are inferred as PostgreSQL `date` values, so the audited builders do not cast a typed `timestamptz` parameter through the connection TimeZone. Profile cohorts explicitly use `AT TIME ZONE`.
- Realtime minute merge is bounded to 30 slots. Platform store lookups other than API-key prefix have matching indexes; no Go DB-query loop was found there.
- `LATERAL VALUES` in rollup construction is a fixed 17-row expansion, not a large-table correlated scan. Session-detail partition probes are indexed and bounded by the session/timeline limits.

Verification: `gofmt` clean, `go vet ./...` passed, and `SUPERMETRY_TEST_DSN=… go test ./...` passed (including `internal/query` in 429.8 s).
